Textrawl splits documents into chunks for efficient embedding and retrieval. The chunking strategy balances context preservation with search precision.

## Why Chunk?

### Embedding Model Limits

Embedding models have token limits:

| Model | Max Tokens |
|-------|------------|
| text-embedding-3-small (OpenAI) | 8,191 |
| nomic-embed-text (Ollama) | 8,192 |

Large documents must be split to fit.

### Search Precision

Smaller chunks enable more precise results:

- Full document embedding: "This document is somewhat relevant"
- Chunk embedding: "This specific paragraph answers the question"

### Cost Efficiency

Embedding costs scale with tokens. Efficient chunking minimizes wasted tokens.

## Textrawl's Approach

### Parameters

| Parameter | Value | Rationale |
|-----------|-------|-----------|
| Max chunk size | 512 tokens | Good balance of context and precision |
| Overlap | 50 tokens | Preserves context across boundaries |
| Strategy | Paragraph-aware | Respects document structure |

### Algorithm

```text
Document
    │
    ▼
Split on paragraphs (double newline)
    │
    ▼
For each paragraph:
    │
    ├── If < 512 tokens: Keep as chunk
    │
    └── If > 512 tokens: Split at sentence boundaries
                │
                ▼
        Add 50-token overlap with previous chunk
```

### Example

Input document (800 tokens total):

```markdown
# Project Overview

This project aims to improve search capabilities...
[200 tokens of content]

## Architecture

The system consists of three main components...
[400 tokens of content]

## Implementation

We will implement in three phases...
[200 tokens of content]
```

Output chunks:

| Chunk | Content | Tokens |
|-------|---------|--------|
| 1 | "# Project Overview\n\nThis project aims to..." | 200 |
| 2 | "## Architecture\n\nThe system consists of..." | 400 |
| 3 | "## Implementation\n\nWe will implement..." | 200 |

## Overlap Strategy

### Why Overlap?

Without overlap, information at chunk boundaries is lost:

```text
Chunk 1: "...the budget was approved by"
Chunk 2: "the finance committee on Tuesday."

Query: "Who approved the budget?"
→ Neither chunk contains the full answer
```

With overlap:

```text
Chunk 1: "...the budget was approved by the finance committee"
Chunk 2: "approved by the finance committee on Tuesday..."

Query: "Who approved the budget?"
→ Both chunks contain relevant context
```

### 50-Token Overlap

Why 50 tokens (~200 characters)?

- Covers most sentence boundaries
- Captures context without excessive duplication
- ~10% overhead (acceptable for search quality)

## Paragraph-Aware Splitting

### Benefits

1. **Respects structure**: Doesn't split mid-sentence
2. **Preserves meaning**: Keeps related ideas together
3. **Better embeddings**: More coherent text = better vectors

### How It Works

1. Split on `\n\n` (double newline)
2. If paragraph > 512 tokens, split on sentence boundaries
3. If still > 512 tokens, split on word boundaries
4. Add overlap from previous chunk

### Markdown Handling

Markdown structure is preserved:

```markdown
# Heading         → Chunk boundary
                  → New chunk starts with heading
## Subheading     → May split or not (depends on size)

Paragraph text... → Kept together if < 512 tokens
```

## Token Counting

### Approximate Conversion

| Content Type | Chars per Token |
|--------------|-----------------|
| English text | ~4 |
| Code | ~2-3 |
| Technical docs | ~3-4 |

512 tokens ≈ 2048 characters

### Accurate Counting

Textrawl uses tiktoken for accurate token counting:

```typescript
import { encoding_for_model } from 'tiktoken';

const encoder = encoding_for_model('text-embedding-3-small');
const tokens = encoder.encode(text);
console.log(tokens.length); // Actual token count
```

## Chunk Metadata

Each chunk stores:

```typescript
{
  id: "uuid",
  documentId: "parent-doc-uuid",
  content: "chunk text...",
  chunkIndex: 0,           // Position in document
  startOffset: 0,          // Character offset
  endOffset: 2048,         // Character offset
  embedding: [...],        // Vector embedding
  metadata: {
    tokenCount: 512
  }
}
```

## Retrieval Flow

```text
Search Query
     │
     ▼
Generate query embedding
     │
     ▼
Find similar chunks (semantic)
Find matching chunks (full-text)
     │
     ▼
Return chunks with document context
     │
     ▼
User can request full document via get_document
```

## Best Practices

### Writing for Good Chunks

1. **Use headings**: Create natural break points
2. **Keep paragraphs focused**: One idea per paragraph
3. **Avoid very long paragraphs**: > 512 tokens get split
4. **Use markdown structure**: Lists, code blocks, etc.

### Content That Chunks Well

✅ Good:
- Meeting notes with clear sections
- Documentation with headings
- Articles with paragraphs
- Emails (naturally short)

⚠️ Challenging:
- Very long code blocks (may split mid-function)
- Dense technical specifications
- Tables (may lose context)

## Debugging Chunks

### View Chunks for a Document

```typescript
// Using get_document with includeChunks
{
  "documentId": "uuid",
  "includeChunks": true
}
```

Response shows all chunks:

```json
{
  "document": { ... },
  "chunks": [
    { "index": 0, "content": "..." },
    { "index": 1, "content": "..." }
  ]
}
```

### Check Chunk Count

```sql
SELECT document_id, COUNT(*) as chunk_count
FROM chunks
GROUP BY document_id
ORDER BY chunk_count DESC;
```

Very high chunk counts may indicate:
- Very large documents (consider splitting)
- Chunking parameters need adjustment
